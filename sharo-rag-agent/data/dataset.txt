Detailed Dataset Description for the "Sharko" Project (Australia)

The "Sharko" project's predictive capabilities are built upon a dataset covering Australian coastal waters (lon 110-160E, lat 9-46S), integrating real satellite and forecast ocean data with shark occurrence records collected in and around Australia from 2020 to today. The dataset is designed to provide a comprehensive view of the oceanic conditions that correlate with shark presence in Australian waters specifically, rather than a global generalisation.

1. Data Sources

Shark occurrence data (target variable): drawn from three sources and merged into a single, cleaned, de-duplicated file (data/sharks_australia.csv).

- OBIS (Ocean Biodiversity Information System, api.obis.org): includes IMOS acoustic shark tag detections, iNaturalist citizen-science sightings, and BRUVS (baited remote underwater video survey) records.

- GBIF (Global Biodiversity Information Facility, api.gbif.org) / Atlas of Living Australia: additional occurrence records for Australian shark species.

- Queensland Shark Control Program (data.qld.gov.au): real beach-net and drumline catch records, plus the locations of the control gear itself, from Queensland's long-running shark mitigation program.

Environmental data (predictive features): all sourced from Copernicus Marine Service and NOAA, subset to the Australian bounding box rather than downloaded globally.

- Sea Surface Temperature: Copernicus Marine OSTIA Level 4 product, daily, approximately 0.05-degree resolution.

- Sea level anomaly, dynamic topography and surface currents: Copernicus Marine DUACS Level 4 product, daily, approximately 0.125-degree resolution.

- Chlorophyll-a: Copernicus Marine GlobColour gap-free Level 4 product, daily, approximately 4 km resolution. Chlorophyll-a is a proxy for primary productivity (phytoplankton abundance), which underpins the marine food web that ultimately draws sharks to an area.

- Depth and distance to coast: NOAA ETOPO 1 arc-minute bathymetry, accessed via ERDDAP, approximately 1.8 km resolution.

2. Data Preprocessing and Feature Engineering

- Temporal and spatial alignment: satellite and bathymetry data, provided in NetCDF format, is loaded with xarray. Each shark record's date and coordinates are snapped to the nearest ocean grid cell (never land) for every source, since each source can have a slightly different coastal mask.

- Missing-value handling: cells with no data within a set snapping distance are treated as missing rather than guessed at; a record only enters the training set once every required feature is present.

- Feature engineering (temporal): day-of-year is transformed into sinusoidal (day_sin) and cosinusoidal (day_cos) components. This captures the cyclic nature of seasonality (for example breeding or migration timing) without imposing an artificial linear relationship.

- Feature engineering (spatial): beyond the raw satellite values, a temperature front (the spatial gradient of sea surface temperature, in degrees C per km) is computed, since sharks are known to key in on temperature boundaries rather than just absolute temperature.

- Occurrence cleaning: records with missing or invalid coordinates, or coordinates on land or outside Australian waters, are removed. Duplicate records (same identity, location and date) are removed.

- Latitude and longitude are intentionally excluded from the final model feature set (see model_traning.txt): including them would let the model learn "where the sensors, divers or beaches are" rather than the actual ocean conditions sharks respond to.

- Pseudo-absence / background points: for every confirmed presence, a matched set of background points is generated to represent "no confirmed sighting" locations, and sightings are weighted equally against background points during training (balanced sample weights) rather than duplicated, since real sightings are far more spatially clustered than the background.

3. Final Dataset Composition

Two dataset variants are built from the same underlying records:

- The daily dataset (data/model_dataset.csv.gz): each record paired with the real satellite ocean conditions of that exact day. Used to train the "daily" models.

- The seasonal dataset (data/model_dataset_seasonal.csv.gz): each record paired instead with the typical/climatological conditions for that place and week of year (built by 12_build_climatology.py from the full daily archive, 2020-2026). Used to train the long-range "seasonal" models that don't depend on having real-time ocean data, so the same API can still answer for a date years in the future.

For each entry, the dataset includes: decimalLatitude, decimalLongitude (retained for spatial cross-validation and the known-range check, but not used as model features), day_sin, day_cos, sst_c (sea temperature), sst_front (temperature front), chl_log10 (chlorophyll, log10), sla_m (sea level anomaly), adt_m (dynamic topography), current_ms (current speed), depth_m, dist_coast_km, species (for species-specific subsets), and presence (target variable: 1 for a real sighting, 0 for a background point).

This dataset lets the models learn the environmental signatures associated with each species' presence specifically in Australian waters, and, through the seasonal variant, still produce scientifically grounded predictions for dates where no real ocean measurement exists yet.
